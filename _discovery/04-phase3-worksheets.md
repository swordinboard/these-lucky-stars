### C1d. Cohort gaps

A tag carried by most of a namespace but missing from some members. Three
kinds of gap are excluded because they are correct by definition and were only
noise: **category tags** (`core`, `sci-fi`) track `category`, not a cohort;
**framework blocks** are not instances of what they introduce; and the
**mutually exclusive group tags** `battery`, `general`, `luck` — each ability carries
exactly one, so the others are meant to be missing. That last exclusion was
confirmed on review and removed 12 false positives per run.

## C4. Feature prerequisites — the three places they are written

A feature's prerequisites are stated in three places, each doing a different
job. This section reports where they disagree, so drift surfaces instead of
sitting in the data.

1. **The prerequisite line** in the block's own text — what a reader sees.
2. **`requires:`** in frontmatter — the mechanical rule the PDF builder obeys.
   By decision it holds *features only*: attributes, levels, items and
   category conditions ("any tool kit") stay prose.
3. **The index nesting** (`- ` / `-- ` in a catalog) — where a reader meets
   the entry. Recorded as `listed_under`.

**2 and 3 are not the same thing and must not be merged.** They agree today,
but 39 `requires` point into a different list entirely, which no index tree
can show — so neither can be generated from the other.

### `requires` against the prerequisite line

**No disagreements** across 54 features that carry `requires`.

Every one is exactly the set of feature links in its own prerequisite line.
**Nothing to do here — this is a regression check, not an open item.** It
passes on every run and stays in the worksheet so that if a prerequisite
line and its `requires` ever drift apart, the count above stops being zero.
The three real errors it caught — Slip Strike, Long Performance, Fast Kit
Trap — were fixed when it was written.

### `requires` against the index nesting

Differences here are expected — the two answer different questions. Read it
as a review list, not an error list.

29 blocks are nested in an index; **0** are nested under
something they do not require.


Also worth remembering: **39** `requires` point at a feature in another
list (abilities depending on proficiencies or traits). No index tree can show
those, which is the other reason the nesting cannot be generated from them.

## C3. Self-containment — blocks that point outside themselves

A block has to read correctly when a GM prints it alone, with none of its
page around it. This flags **deictic language** — text pointing at something
outside the block: `above`, `below`, `this page`, `the following`,
`as described`, `see the`.

Two filters run first, or the list is mostly noise:

- **Comparisons are dropped.** "stress drops below threshold" and "well below
  max carry weight" are measurements, not pointers.
- **In-block referents are dropped.** "use the chart below" is fine when the
  chart is the next line of the same block. Those are listed separately.

`see the [Martial Training] proficiency` survives being printed alone — the
reader can follow it. **Unlinked deixis is the bug**, because nothing in the
printed page tells the reader where to look.

Scanned 434 blocks. **8** point outside themselves; of

## C7. Heading migration — blocks with no heading of their own

Blocks no longer carry their own heading; the call site picks the level and
the shortcode emits it. Core rules is migrated. **These are the call sites
that could not be converted mechanically**, because the block has no heading
to move — giving it a level would *add* a heading that has never been on the
site. Each needs a call.

The four modes, for reference:

| Call | Renders |
|---|---|
| `{{% include "…" %}}` | body only, no name |
| `{{% include "…" "h3" %}}` | `### Title` then the body |
| `{{% include "…" "lead" %}}` | **Title** — body, run on |
| `{{% include "…" "h3" "false" %}}` | no name, but internals positioned at h4 |

### C7a. Opens with its own bold lead-in — 0 call sites

Your call in §C5 was that **the bold lead-in is the heading** — an inline,
low-tier list header. If that is right, these convert to `"lead"`: the
hand-written `**Name**` comes out of the snippet and the shortcode emits it
from `title` instead, so the name is single-sourced like everywhere else.

Rendered output is the same either way. What changes is that the name stops
being typed inside the block. **The `*(3 AP)*` part stays in the prose** — it
is not part of the name, and every one of these restates the cost in the body
(checked; `rules/combat/stealth` has no cost and says so).


### C7b. No lead-in either — 9 call sites

These render with no name at all. They sit under a group heading that names
something broader, or follow another block as a continuation. Leaving them
bare is legitimate; the question is whether each *should* be findable on its
own, since the PDF builder will print `title` for them regardless.

*9 call sites across 7 blocks reviewed and left bare: `rules/actions/standard-actions`, `rules/combat/actions-in-combat`, `rules/movement/speed-tiers`, `rules/movement/speed-tiers-chart`, `rules/objects/armor-degradation`, `rules/objects/overview`, `rules/objects/shield-degradation`.*

- nothing left

### C7c. Page and block disagree on the name

Converted with `"false"`, so the page keeps its own heading and the block
supplies no name. That is right where the heading names a *group*, and a
smell where it names the same single block twice over.

*5 reviewed — keep both names. The page heading names the section, the block names itself, and the two doing different jobs is the point.*


### C7d. One anchor drifted

`rules/movement/speed-tiers-chart` moved from `#speed-tiers` to `#speed`. It is a
bare block, so its anchor is inherited from whatever heading precedes it, and
that heading became a generated one. Nothing links to it and the site has zero
broken links — but **a bare block's anchor is a side effect of its neighbour**,
which is the real argument for resolving C7a and C7b. Its old anchor was a
duplicate of `rules/movement/speed-tiers` anyway, so neither value was correct.

**Settled: left anchorless.** It is a chart belonging to Speed Tiers, not a
thing a reader looks up on its own.

## C6. Internal sub-headings — the h2 convention

§C5 is about a block's own title. This is about headings **inside** a block.

### Heading level is the bigger print problem

The blocks that *own* a heading hard-code its level in their markdown:

- **h3** — 1 blocks

So a GM who assembles a PDF and puts one of those at a different depth gets a

mattering at print time.
